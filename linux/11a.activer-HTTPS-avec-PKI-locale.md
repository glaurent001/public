# 1. Concepts clés avant de commencer

## 1.1. Qu'est-ce qu'une PKI (Public Key Infrastructure) ?

Une PKI est un ensemble de mécanismes permettant de **garantir l'identité** d'un serveur (ou d'un utilisateur) grâce à des certificats numériques.

Le principe repose sur une **chaîne de confiance** :

```
Autorité de Certification (CA)
        │
        │  signe
        ▼
Certificat du serveur web
        │
        │  présenté au
        ▼
Navigateur du client
```

Le navigateur fait confiance au serveur **parce qu'il fait confiance à la CA** qui a signé son certificat.

## 1.2. Les acteurs du processus

| Acteur | Rôle |
|--------|------|
| **CA (Certificate Authority)** | Autorité qui signe et garantit les certificats |
| **Serveur web** | Entité dont on veut prouver l'identité |
| **Client (navigateur)** | Vérifie la chaîne de confiance |

## 1.3. Les fichiers que nous allons créer

| Fichier | Description |
|---------|-------------|
| `ca.key` | Clé privée de la CA *(à protéger absolument)* |
| `ca.crt` | Certificat public de la CA *(à distribuer aux clients)* |
| `serveur.key` | Clé privée du serveur web *(reste sur le serveur)* |
| `serveur.csr` | Demande de signature de certificat *(envoyée à la CA)* |
| `serveur.crt` | Certificat du serveur signé par la CA *(installé sur le serveur)* |

# 2. Partie 1 — Créer l'Autorité de Certification (CA)

## 2.1. Étape 1.1 — Préparer l'environnement de travail

Créez l'arborescence qui va accueillir les fichiers de votre CA :

```bash
mkdir -p ~/ca/{private,certs,requests}
chmod 700 ~/ca/private
cd ~/ca
```

> **Pourquoi `chmod 700` ?**  
> Le répertoire `private` contient la clé secrète de la CA. Le restreindre en lecture/écriture à l'utilisateur courant uniquement est une mesure de sécurité de base.

---

## 2.2. Étape 1.2 — Générer la clé privée de la CA

```bash
openssl genrsa -aes256 -out ~/ca/private/ca.key 4096
```

**Décryptage de la commande :**

| Paramètre | Signification |
|-----------|---------------|
| `genrsa` | Génère une paire de clés RSA |
| `-aes256` | Chiffre la clé privée avec AES-256 (protège avec une passphrase) |
| `-out` | Fichier de sortie |
| `4096` | Taille de la clé en bits |

> **Pourquoi 4096 bits pour la CA ?**  
> La clé de la CA signe tous les autres certificats. Elle doit être la plus robuste possible. Pour les serveurs, 2048 bits suffisent (bon compromis performances/sécurité).

OpenSSL vous demande de saisir une **passphrase** : choisissez-en une solide et ne l'oubliez pas. Elle sera demandée à chaque signature de certificat.

Vérifiez la clé générée :

```bash
openssl rsa -noout -text -in ~/ca/private/ca.key
```

---

## 2.3. Étape 1.3 — Créer le certificat auto-signé de la CA

C'est ici que la CA se "certifie elle-même". Ce certificat sera importé sur les postes clients pour établir la chaîne de confiance.

```bash
openssl req -new -x509 -days 3650 -key ~/ca/private/ca.key -out ~/ca/certs/ca.crt
```

**Décryptage de la commande :**

| Paramètre | Signification |
|-----------|---------------|
| `req` | Gestion des requêtes et certificats |
| `-new` | Nouveau certificat |
| `-x509` | Format standard des certificats (produit directement un certificat, pas un CSR) |
| `-days 3650` | Valide 10 ans (acceptable pour une CA interne) |
| `-key` | Clé privée utilisée pour signer |
| `-out` | Fichier de sortie |

OpenSSL vous demande de renseigner les **informations d'identité** (Distinguished Name) :

```
Country Name (2 letter code) [AU]: FR
State or Province Name (full name) []: Hauts-de-France
Locality Name (eg, city) []: Armentieres
Organization Name (eg, company) []: BTS CIEL
Organizational Unit Name (eg, section) []: Laboratoire TP
Common Name (e.g. server FQDN or YOUR name) []: CA Intranet TP
Email Address []: admin@intranet.tp
```

> **Le Common Name (CN) de la CA** doit être explicite. Les navigateurs l'affichent dans la liste des CA de confiance.

Vérifiez le certificat CA créé :

```bash
openssl x509 -noout -text -in ~/ca/certs/ca.crt
```

Cherchez dans la sortie :
- `Issuer` et `Subject` : identiques (c'est bien **auto-signé**)
- `CA:TRUE` dans les extensions : confirme que c'est bien une autorité

# 3. Partie 2 — Créer un certificat pour le serveur web

Le processus se déroule en **3 étapes** qui simulent une situation réelle : le serveur génère sa clé et une demande (CSR), la CA vérifie et signe, le serveur installe son certificat.

```
[Serveur]                          [CA]
    │                               │
    │── génère sa clé privée ───▶  │
    │── crée un CSR ─────────────▶ │
    │                               │── vérifie le CSR
    │                               │── signe le certificat
    │◀── reçoit le certificat ────  │
    │                               │
    │── installe clé + certificat   │
```

---

## 3.1. Étape 2.1 — Générer la clé privée du serveur

```bash
openssl genrsa -out ~/ca/private/serveur.key 2048
```

> **Remarquez l'absence de `-aes256`** : on ne chiffre pas la clé du serveur avec une passphrase. En effet, Apache/Nginx doit pouvoir la lire **automatiquement au démarrage**, sans intervention humaine.  
> En contrepartie, **le fichier doit être protégé en permissions** (`chmod 400`).

```bash
chmod 400 ~/ca/private/serveur.key
```

---

## 3.2. Étape 2.2 — Créer le fichier de configuration des extensions (SAN)

Depuis 2017, les navigateurs modernes (Chrome, Firefox) **ignorent le Common Name** et utilisent exclusivement le champ **Subject Alternative Name (SAN)** pour valider le nom du serveur.

Créez le fichier de configuration `~/ca/serveur-ext.cnf` :

```ini
[ req ]
default_bits       = 2048
default_md         = sha256
distinguished_name = req_distinguished_name
req_extensions     = req_ext
prompt             = no

[ req_distinguished_name ]
countryName            = FR
stateOrProvinceName    = Hauts-de-France
localityName           = Armentieres
organizationName       = BTS CIEL
commonName             = serveur.intranet.tp

[ req_ext ]
subjectAltName = @alt_names

[ alt_names ]
DNS.1 = serveur.intranet.tp
DNS.2 = serveur
IP.1  = 192.168.1.10
```

> **Adaptez** `DNS.1`, `DNS.2` et `IP.1` à votre environnement de TP.  
> Vous pouvez ajouter autant de `DNS.x` et `IP.x` que nécessaire.

---

## 3.3. Étape 2.3 — Générer le CSR (Certificate Signing Request)

Le CSR est une **demande de certificat** : il contient l'identité du serveur et sa clé publique, signé par sa propre clé privée (preuve qu'il en est bien le propriétaire).

```bash
openssl req -new -key ~/ca/private/serveur.key -config ~/ca/serveur-ext.cnf -out ~/ca/requests/serveur.csr
```

**Décryptage de la commande :**

| Paramètre | Signification |
|-----------|---------------|
| `req -new` | Crée une nouvelle demande de certificat |
| `-key` | Clé privée du demandeur |
| `-config` | Fichier de configuration avec les SAN |
| `-out` | Fichier CSR produit |

Inspectez le CSR pour vérifier son contenu :

```bash
openssl req -noout -text -in ~/ca/requests/serveur.csr
```

Vérifiez que vous voyez bien la section `X509v3 Subject Alternative Name` avec vos DNS et IP.

> **En entreprise**, c'est ce fichier `.csr` qui serait envoyé à une CA commerciale (DigiCert, Let's Encrypt...) ou à la CA interne. La **clé privée ne quitte jamais le serveur**.

---

## 3.4. Étape 2.4 — Signer le CSR avec la CA

C'est l'opération centrale : la CA **vérifie la demande et appose sa signature**.

```bash
openssl x509 -req -days 375 -in ~/ca/requests/serveur.csr -CA ~/ca/certs/ca.crt -CAkey ~/ca/private/ca.key -CAcreateserial -extfile ~/ca/serveur-ext.cnf -extensions req_ext -out ~/ca/certs/serveur.crt
```

**Décryptage de la commande :**

| Paramètre | Signification |
|-----------|---------------|
| `x509 -req` | Traitement d'un CSR pour produire un certificat |
| `-days 375` | Durée de validité (< 398 jours, limite imposée par les navigateurs) |
| `-in` | CSR en entrée |
| `-CA` | Certificat de la CA signataire |
| `-CAkey` | Clé privée de la CA (la passphrase sera demandée) |
| `-CAcreateserial` | Crée un numéro de série unique pour ce certificat |
| `-extfile` | Fichier contenant les extensions à inclure |
| `-extensions` | Section du fichier à utiliser |
| `-out` | Certificat signé en sortie |

> **Pourquoi 375 jours maximum ?**  
> Depuis septembre 2020, Apple (Safari) refuse les certificats dont la durée dépasse 398 jours. Chrome et Firefox ont suivi. C'est une mesure de sécurité pour forcer le renouvellement régulier.

# 4. Partie 3 — Vérifications

## 4.1. Vérifier le certificat du serveur

```bash
openssl x509 -noout -text -in ~/ca/certs/serveur.crt
```

Contrôlez la présence de :
- `Issuer` : doit correspondre à votre CA
- `Subject` : doit correspondre au serveur
- `X509v3 Subject Alternative Name` : doit lister vos DNS et IP
- `Validity` : dates de début et fin de validité

---

## 4.2. Vérifier la chaîne de confiance

Cette commande vérifie que le certificat du serveur est bien signé par votre CA :

```bash
openssl verify -CAfile ~/ca/certs/ca.crt ~/ca/certs/serveur.crt
```

Résultat attendu :

```
serveur.crt: OK
```

---

## 4.3. Tester la connexion TLS une fois déployé

```bash
openssl s_client -connect serveur.intranet.tp:443 \
    -CAfile ~/ca/certs/ca.crt
```

Cherchez dans la sortie :
```
Verify return code: 0 (ok)
```

# 5. Partie 4 — Déploiement

## 5.1. Fichiers à installer sur le serveur web

```
/etc/ssl/intranet/
├── serveur.crt    ← certificat du serveur (public)
└── serveur.key    ← clé privée (permissions 400, root uniquement)
```

```bash
# Sur le serveur web
sudo cp ~/ca/certs/serveur.crt /etc/ssl/intranet/
sudo cp ~/ca/private/serveur.key /etc/ssl/intranet/
sudo chmod 400 /etc/ssl/intranet/serveur.key
sudo chown root:root /etc/ssl/intranet/serveur.key
```

## 5.2. Configuration Apache

```apache
<VirtualHost *:443>
    ServerName serveur.intranet.tp
    SSLEngine on
    SSLCertificateFile    /etc/ssl/intranet/serveur.crt
    SSLCertificateKeyFile /etc/ssl/intranet/serveur.key

    # Protocoles sécurisés uniquement
    SSLProtocol           all -SSLv3 -TLSv1 -TLSv1.1
    SSLCipherSuite        HIGH:!aNULL:!MD5
    SSLHonorCipherOrder   on
</VirtualHost>
```

## 5.3. Configuration Nginx

```nginx
server {
    listen 443 ssl;
    server_name serveur.intranet.tp;

    ssl_certificate     /etc/ssl/intranet/serveur.crt;
    ssl_certificate_key /etc/ssl/intranet/serveur.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
}
```

---

## 5.4. Installer la CA sur les postes clients

Pour que les navigateurs fassent confiance à votre CA, distribuez `ca.crt` et installez-le :

**Linux (Debian/Ubuntu)**
```bash
sudo cp ca.crt /usr/local/share/ca-certificates/ca-intranet.crt
sudo update-ca-certificates
```

**Windows**
```
Double-clic sur ca.crt
→ Installer le certificat
→ Ordinateur local
→ Placer dans : "Autorités de certification racines de confiance"
```

**Firefox** *(gère son propre magasin de certificats)*
```
about:preferences#privacy
→ Afficher les certificats
→ Onglet "Autorités"
→ Importer → sélectionner ca.crt
→ Cocher "Confirmer cette AC pour identifier des sites web"
```

# 6. Récapitulatif des commandes

```bash
# === CA ===
# 1. Clé privée de la CA (4096 bits, protégée par passphrase)
openssl genrsa -aes256 -out ~/ca/private/ca.key 4096

# 2. Certificat auto-signé de la CA (10 ans)
openssl req -new -x509 -days 3650 -key ~/ca/private/ca.key -out ~/ca/certs/ca.crt

# === SERVEUR ===
# 3. Clé privée du serveur (2048 bits, sans passphrase)
openssl genrsa -out ~/ca/private/serveur.key 2048

# 4. CSR du serveur (avec SAN via serveur-ext.cnf)
openssl req -new -key ~/ca/private/serveur.key -config ~/ca/serveur-ext.cnf -out ~/ca/requests/serveur.csr

# 5. Signature du CSR par la CA
openssl x509 -req -days 375 -in ~/ca/requests/serveur.csr \
    -CA ~/ca/certs/ca.crt -CAkey ~/ca/private/ca.key \
    -CAcreateserial -extfile ~/ca/serveur-ext.cnf -extensions req_ext \
    -out ~/ca/certs/serveur.crt

# === VÉRIFICATIONS ===
openssl verify -CAfile ~/ca/certs/ca.crt ~/ca/certs/serveur.crt
openssl x509 -noout -text -in ~/ca/certs/serveur.crt
```

# 7. Points de réflexion pour aller plus loin

1. **Révocation** : que se passe-t-il si une clé privée est compromise ? Comment informer les clients qu'un certificat n'est plus valide ? *(CRL, OCSP)*

2. **Hiérarchie CA** : en entreprise, on distingue souvent une CA racine (hors ligne) et des CA intermédiaires (en ligne). Pourquoi ?

3. **Let's Encrypt** : quel protocole utilise-t-il pour automatiser l'émission de certificats ? Pourquoi ne peut-on pas l'utiliser pour un intranet ?

4. **Durée de validité** : pourquoi réduire la durée de validité des certificats améliore-t-elle la sécurité globale ?
