# 1. Prérequis

Avoir réalisé le TP PKI OpenSSL (CA racine + certificat serveur)  


# 2. Objectif et architecture cible

Dans le TP précédent, vous avez créé manuellement une CA OpenSSL et des certificats. Ce processus manuel est acceptable pour quelques serveurs, mais devient ingérable à l'échelle :

- Surveiller les dates d'expiration de dizaines de certificats
- Se souvenir des commandes OpenSSL à chaque renouvellement
- Risquer une coupure de service si un certificat expire inaperçu

**step-ca** est un serveur CA léger qui expose un **endpoint ACME** (le même protocole que Let's Encrypt) sur votre intranet. Les serveurs s'y inscrivent une fois, puis renouvellent leur certificat **automatiquement** sans intervention humaine.

## 2.1. Architecture cible

```
┌─────────────────────────────────────────────────────┐
│                    INTRANET TP                      │
│                                                     │
│  ┌──────────────┐        ┌─────────────────────┐   │
│  │  CA Racine   │ signe  │     step-ca         │   │
│  │  (OpenSSL)   │───────▶│  CA Intermédiaire   │   │
│  │  hors ligne  │        │  endpoint ACME      │   │
│  └──────────────┘        └──────────┬──────────┘   │
│                                     │               │
│                          signe et renouvelle        │
│                                     │               │
│                    ┌────────────────┼────────────┐  │
│                    ▼                ▼            ▼  │
│              Serveur TP1      Serveur TP2    TP3... │
│              (certbot/        (certbot/             │
│               step-cli)        step-cli)            │
└─────────────────────────────────────────────────────┘
```

**Rôle de chaque composant :**

| Composant | Rôle | État |
|-----------|------|------|
| CA Racine OpenSSL | Ancre de confiance, signe step-ca | Hors ligne sauf maintenance |
| step-ca | CA intermédiaire, serveur ACME intranet | Toujours en ligne |
| step-cli / certbot | Client ACME sur chaque serveur | Tourne en daemon |

# 4. Partie 2 — Créer la CA intermédiaire step-ca signée par OpenSSL

step-ca va fonctionner comme une **CA intermédiaire**. Sa propre clé et son certificat seront signés par votre CA racine OpenSSL du TP précédent.

## 4.1. Étape 2.1 — Générer la clé privée de step-ca

```bash
# Sur le serveur step-ca
mkdir -p ~/.step/secrets
openssl genrsa -out ~/.step/secrets/intermediate.key 4096
chmod 400 ~/.step/secrets/intermediate.key
```

## 4.2. Étape 2.2 — Générer le CSR de step-ca

```bash
openssl req -new \
    -key ~/.step/secrets/intermediate.key \
    -out ~/step-ca-intermediate.csr \
    -subj "/C=FR/ST=Bretagne/L=Rennes/O=BTS CIEL/CN=step-ca Intranet TP"
```

## 4.3. Étape 2.3 — Signer le CSR avec votre CA racine OpenSSL

Cette étape se fait sur la machine qui héberge la CA racine OpenSSL.

Créez d'abord le fichier d'extensions pour la CA intermédiaire :

```bash
# Fichier ~/ca/intermediate-ext.cnf
cat > ~/ca/intermediate-ext.cnf << 'EOF'
[ v3_intermediate_ca ]
subjectKeyIdentifier   = hash
authorityKeyIdentifier = keyid:always,issuer
basicConstraints       = critical, CA:true, pathlen:0
keyUsage               = critical, digitalSignature, cRLSign, keyCertSign
EOF
```

> **`pathlen:0`** : cette CA intermédiaire peut signer des certificats finaux, mais ne peut **pas** créer d'autres CA en dessous d'elle. C'est une contrainte de sécurité importante.

Signez le CSR :

```bash
openssl x509 -req \
    -days 1825 \
    -in ~/step-ca-intermediate.csr \
    -CA ~/ca/certs/ca.crt \
    -CAkey ~/ca/private/ca.key \
    -CAcreateserial \
    -extfile ~/ca/intermediate-ext.cnf \
    -extensions v3_intermediate_ca \
    -out ~/ca/certs/intermediate.crt

# Vérifier la signature
openssl verify -CAfile ~/ca/certs/ca.crt ~/ca/certs/intermediate.crt
```

> **Durée 1825 jours (5 ans) :** la CA intermédiaire peut avoir une durée plus longue que les certificats finaux qu'elle émet. Elle reste inférieure à la CA racine (10 ans).

## 4.4. Étape 2.4 — Transférer les fichiers vers le serveur step-ca

```bash
# Copier vers le serveur step-ca (adapter l'IP)
scp ~/ca/certs/intermediate.crt user@step-ca-server:~/.step/secrets/
scp ~/ca/certs/ca.crt user@step-ca-server:~/.step/secrets/
```

# 5. Partie 3 — Initialiser et configurer step-ca

## 5.1. Étape 3.1 — Initialiser step-ca avec la CA intermédiaire

```bash
step ca init \
    --name "CA Intranet TP" \
    --dns "step-ca.intranet.tp" \
    --address ":9000" \
    --root ~/.step/secrets/ca.crt \
    --intermediate-cert ~/.step/secrets/intermediate.crt \
    --intermediate-key ~/.step/secrets/intermediate.key \
    --deployment-type standalone
```

Cette commande crée la structure de configuration dans `~/.step/` :

```
~/.step/
├── config/
│   └── ca.json          ← configuration principale
├── secrets/
│   ├── ca.crt           ← certificat CA racine
│   ├── intermediate.crt ← certificat CA intermédiaire
│   └── intermediate.key ← clé privée intermédiaire
└── db/                  ← base de données des certificats émis
```

## 5.2. Étape 3.2 — Activer le provisioner ACME

Le fichier `~/.step/config/ca.json` doit contenir un provisioner de type ACME. Éditez-le pour ajouter le bloc suivant dans le tableau `"provisioners"` :

```json
{
    "type": "ACME",
    "name": "acme",
    "forceCN": true,
    "claims": {
        "minTLSCertDuration": "24h",
        "maxTLSCertDuration": "2160h",
        "defaultTLSCertDuration": "2160h"
    }
}
```

> **`maxTLSCertDuration: 2160h`** correspond à 90 jours — cohérent avec les bonnes pratiques actuelles.

Le fichier `ca.json` complet ressemble à ceci :

```json
{
    "root": "/home/user/.step/secrets/ca.crt",
    "federatedRoots": [],
    "crt": "/home/user/.step/secrets/intermediate.crt",
    "key": "/home/user/.step/secrets/intermediate.key",
    "address": ":9000",
    "dnsNames": ["step-ca.intranet.tp"],
    "logger": {"format": "text"},
    "db": {
        "type": "badgerV2",
        "dataSource": "/home/user/.step/db"
    },
    "authority": {
        "provisioners": [
            {
                "type": "ACME",
                "name": "acme",
                "forceCN": true,
                "claims": {
                    "minTLSCertDuration": "24h",
                    "maxTLSCertDuration": "2160h",
                    "defaultTLSCertDuration": "2160h"
                }
            }
        ]
    },
    "tls": {
        "minVersion": 1.2,
        "maxVersion": 1.3,
        "renegotiation": false
    }
}
```

## 5.3. Étape 3.3 — Lancer step-ca en service systemd

Créez le fichier de service :

```bash
sudo tee /etc/systemd/system/step-ca.service << 'EOF'
[Unit]
Description=step-ca ACME Certificate Authority
Documentation=https://smallstep.com/docs/step-ca
After=network.target

[Service]
Type=simple
User=step
Group=step
ExecStart=/usr/bin/step-ca /home/step/.step/config/ca.json
Restart=on-failure
RestartSec=10
# Sécurisation du service
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=read-only
ReadWritePaths=/home/step/.step/db

[Install]
WantedBy=multi-user.target
EOF
```

```bash
# Créer l'utilisateur dédié
sudo useradd --system --home /home/step --shell /bin/false step
sudo mkdir -p /home/step/.step
sudo cp -r ~/.step/* /home/step/.step/
sudo chown -R step:step /home/step/.step

# Activer et démarrer le service
sudo systemctl daemon-reload
sudo systemctl enable step-ca
sudo systemctl start step-ca
sudo systemctl status step-ca
```

Vérifiez que step-ca répond :

```bash
curl -k https://step-ca.intranet.tp:9000/acme/acme/directory
```

Vous devez obtenir un JSON décrivant les endpoints ACME.

# 6. Partie 4 — Obtenir et renouveler automatiquement un certificat

Deux clients ACME sont présentés : **step-cli** (natif Smallstep) et **certbot** (universel).

## 6.1. Option A — avec step-cli (recommandé sur Linux)

## 6.2. Première obtention du certificat

Sur le serveur client (ex: tp1.intranet.tp) :

```bash
# Enregistrer la CA racine comme source de confiance
step ca bootstrap \
    --ca-url https://step-ca.intranet.tp:9000 \
    --fingerprint $(step certificate fingerprint ~/.step/secrets/ca.crt)

# Obtenir le certificat via ACME
step ca certificate tp1.intranet.tp \
    /etc/ssl/intranet/tp1.crt \
    /etc/ssl/intranet/tp1.key \
    --provisioner acme \
    --san tp1.intranet.tp \
    --san 192.168.1.10
```

## 6.3. Configurer le renouvellement automatique avec step-cli

```bash
# Créer le service de renouvellement automatique
step ca renew \
    --daemon \
    --output-file /etc/ssl/intranet/tp1.crt \
    --output-key /etc/ssl/intranet/tp1.key \
    --exec "systemctl reload apache2"
```

Ou via un service systemd dédié :

```bash
sudo tee /etc/systemd/system/cert-renew-tp1.service << 'EOF'
[Unit]
Description=Renouvellement automatique certificat tp1
After=network.target

[Service]
Type=oneshot
ExecStart=/usr/bin/step ca renew \
    /etc/ssl/intranet/tp1.crt \
    /etc/ssl/intranet/tp1.key \
    --expires-in 720h \
    --exec "systemctl reload apache2"
User=root
EOF

sudo tee /etc/systemd/system/cert-renew-tp1.timer << 'EOF'
[Unit]
Description=Vérification renouvellement certificat tp1 (toutes les 12h)

[Timer]
OnBootSec=5min
OnUnitActiveSec=12h
RandomizedDelaySec=1h

[Install]
WantedBy=timers.target
EOF

sudo systemctl enable --now cert-renew-tp1.timer
```

> **`--expires-in 720h`** : ne renouvelle que si le certificat expire dans moins de 30 jours. Le timer toutes les 12h garantit plusieurs tentatives avant l'expiration.

## 6.4. Option B — avec Certbot (universel, Linux/Windows)

Certbot est le client ACME le plus répandu. Il fonctionne avec n'importe quel serveur ACME, pas uniquement Let's Encrypt.

## 6.5. Installation

```bash
# Debian/Ubuntu
sudo apt install certbot python3-certbot-apache   # pour Apache
sudo apt install certbot python3-certbot-nginx    # pour Nginx
```

## 6.6. Configurer Certbot pour utiliser step-ca

Certbot utilise Let's Encrypt par défaut. Pour pointer vers step-ca, on utilise `--server` :

```bash
# Obtenir le certificat (exemple Apache)
sudo certbot --apache \
    --server https://step-ca.intranet.tp:9000/acme/acme/directory \
    -d tp1.intranet.tp \
    --agree-tos \
    --email admin@intranet.tp
```

> **Problème de confiance :** certbot doit faire confiance à votre CA racine. Installez-la dans le magasin système **avant** de lancer certbot :
> ```bash
> sudo cp ca.crt /usr/local/share/ca-certificates/ca-intranet.crt
> sudo update-ca-certificates
> ```

## 6.7. Vérifier le renouvellement automatique

Certbot installe automatiquement un timer systemd ou une entrée cron :

```bash
# Vérifier le timer
systemctl status certbot.timer

# Tester le renouvellement (sans l'effectuer réellement)
sudo certbot renew --dry-run \
    --server https://step-ca.intranet.tp:9000/acme/acme/directory
```

# 7. Partie 5 — Vérifications et supervision

## 7.1. Vérifier un certificat émis par step-ca

```bash
# Inspecter le certificat
openssl x509 -noout -text -in /etc/ssl/intranet/tp1.crt

# Vérifier la chaîne complète (racine OpenSSL → step-ca → certificat serveur)
openssl verify \
    -CAfile /usr/local/share/ca-certificates/ca-intranet.crt \
    -untrusted ~/.step/secrets/intermediate.crt \
    /etc/ssl/intranet/tp1.crt
```

## 7.2. Lister les certificats émis par step-ca

```bash
# Sur le serveur step-ca
step ca admin list

# Voir les certificats actifs
step ca certificate list
```

## 7.3. Consulter les logs de step-ca

```bash
sudo journalctl -u step-ca -f
```

## 7.4. Surveiller les expirations

```bash
# Vérifier la date d'expiration d'un certificat
openssl x509 -noout -enddate -in /etc/ssl/intranet/tp1.crt

# Script de supervision simple (à intégrer dans un cron)
#!/bin/bash
CERT="/etc/ssl/intranet/tp1.crt"
SEUIL=30  # jours

expiration=$(openssl x509 -noout -enddate -in "$CERT" | cut -d= -f2)
exp_epoch=$(date -d "$expiration" +%s)
now_epoch=$(date +%s)
jours_restants=$(( ($exp_epoch - $now_epoch) / 86400 ))

if [ $jours_restants -lt $SEUIL ]; then
    echo "ALERTE : certificat $CERT expire dans $jours_restants jours !"
    # Envoyer une notification (mail, Slack, etc.)
fi
```

# 8. Récapitulatif de l'architecture déployée

```
CA Racine OpenSSL (ca.crt)
│   Validité : 10 ans
│   État : hors ligne
│
└── CA Intermédiaire step-ca (intermediate.crt)
        Validité : 5 ans
        État : en ligne, expose ACME sur :9000
        │
        ├── tp1.intranet.tp (tp1.crt)  ← renouvelé auto toutes les ~60 jours
        ├── tp2.intranet.tp (tp2.crt)  ← renouvelé auto toutes les ~60 jours
        └── tp3.intranet.tp (tp3.crt)  ← renouvelé auto toutes les ~60 jours
```

**Ce qui se passe automatiquement :**
1. Le timer systemd se déclenche toutes les 12h sur chaque serveur
2. Il vérifie si le certificat expire dans moins de 30 jours
3. Si oui : appel ACME vers step-ca → nouveau certificat émis
4. Apache/Nginx est rechargé (`systemctl reload`) pour prendre en compte le nouveau certificat
5. Aucune intervention humaine requise
