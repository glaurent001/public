# 1. Indisponibilité de step-ca lors du renouvellement

## 1.1. Question

**Que se passe-t-il si step-ca est indisponible** au moment du renouvellement ? Le certificat actuel est-il toujours valide ? Quelle stratégie adopter ?

## 1.2. Le problème

step-ca est une dépendance critique : si elle est indisponible au moment où un client tente de renouveler son certificat, que se passe-t-il ?

## 1.3. Ce qui se passe concrètement

Le certificat **actuellement en service reste valide** jusqu'à sa date d'expiration. Une indisponibilité momentanée de step-ca n'entraîne pas de coupure immédiate du service HTTPS.

```
Scénario :
  Certificat valide jusqu'au 15 avril
  Tentative de renouvellement le 15 mars → step-ca indisponible → ÉCHEC
  Timer re-tente 12h plus tard → step-ca toujours indisponible → ÉCHEC
  ...
  step-ca revient en ligne le 20 mars → renouvellement réussi
  Nouveau certificat valide jusqu'au 18 juin
  ✅ Aucune coupure de service
```

Le danger réel est une **indisponibilité prolongée** qui durerait jusqu'à l'expiration du certificat. D'où l'importance de la stratégie de renouvellement anticipé.

## 1.4. Stratégie de renouvellement anticipé

La bonne pratique est de tenter le renouvellement quand il reste **un tiers de la durée de validité**. Pour un certificat de 90 jours, on renouvelle à partir de 30 jours avant expiration.

```
Durée totale : 90 jours
├── Jours 0–60  : certificat valide, pas de renouvellement
├── Jour 60     : première tentative de renouvellement (30j restants)
├── Jours 60–89 : nouvelles tentatives toutes les 12h si échec
└── Jour 90     : expiration — zone de danger si toutes les tentatives ont échoué
```

Avec le timer systemd toutes les 12h, cela donne **60 tentatives** avant expiration. Il faudrait une indisponibilité de step-ca de 30 jours consécutifs pour provoquer une coupure — ce qui devrait déclencher bien avant une alarme de supervision.

## 1.5. Rendre step-ca hautement disponible

Pour un environnement de production, plusieurs approches existent :

**Option 1 — step-ca en cluster (step-ca HA)**

step-ca supporte une base de données partagée (MySQL, PostgreSQL) permettant de faire tourner plusieurs instances derrière un load balancer :

```
                  ┌─────────────────┐
Clients ACME ────▶│  Load Balancer  │
                  └────────┬────────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
       step-ca instance 1       step-ca instance 2
              └────────────┬────────────┘
                           ▼
                   Base de données
                   partagée (MySQL)
```

**Option 2 — Certificats de secours (backup certs)**

Conserver le certificat précédent comme fallback et basculer dessus si le renouvellement échoue :

```bash
# Script de renouvellement avec fallback
#!/bin/bash
CERT="/etc/ssl/intranet/tp1.crt"
KEY="/etc/ssl/intranet/tp1.key"
BACKUP_CERT="/etc/ssl/intranet/tp1.crt.bak"
BACKUP_KEY="/etc/ssl/intranet/tp1.key.bak"

# Sauvegarder avant tentative
cp $CERT $BACKUP_CERT
cp $KEY $BACKUP_KEY

# Tenter le renouvellement
if step ca renew $CERT $KEY --expires-in 720h; then
    echo "Renouvellement réussi"
    systemctl reload apache2
else
    echo "ÉCHEC du renouvellement — conservation du certificat actuel"
    # Alerter l'administrateur
    echo "ALERTE : renouvellement échoué sur $(hostname)" | mail -s "Alerte PKI" admin@intranet.tp
fi
```

**Option 3 — Supervision proactive**

Mettre en place une supervision des dates d'expiration indépendante du processus de renouvellement :

```bash
# Vérification quotidienne via cron
# Ajouter dans /etc/cron.daily/check-certs
#!/bin/bash
for cert in /etc/ssl/intranet/*.crt; do
    jours=$(( ($(date -d "$(openssl x509 -noout -enddate -in $cert \
        | cut -d= -f2)" +%s) - $(date +%s)) / 86400 ))
    if [ $jours -lt 14 ]; then
        echo "CRITIQUE : $cert expire dans $jours jours" \
            | mail -s "[PKI] Certificat critique" admin@intranet.tp
    fi
done
```

# 2. Révocation d'un certificat depuis step-ca

## 2.1. Question

**Révocation dans ce contexte** : si un serveur est compromis, comment révoquer son certificat depuis step-ca ? Quelle commande utiliser ?

## 2.2. Quand révoquer ?

La révocation est nécessaire quand :
- La **clé privée d'un serveur est compromise** (intrusion, vol de fichier)
- Un serveur est **décommissionné** définitivement
- Les **informations du certificat sont incorrectes** (mauvais nom, mauvaise IP)

## 2.3. Révoquer avec step-cli

```bash
# Sur le serveur step-ca, révoquer par numéro de série
step ca revoke --serial <NUMERO_SERIE>

# Obtenir le numéro de série d'un certificat
openssl x509 -noout -serial -in /etc/ssl/intranet/tp1.crt
# Exemple de sortie : serial=1A2B3C4D5E6F...

# Révoquer en fournissant directement le certificat
step ca revoke --cert /etc/ssl/intranet/tp1.crt \
               --key /etc/ssl/intranet/tp1.key
```

## 2.4. Choisir la raison de révocation (reason codes)

Le protocole X.509 définit des codes de révocation standardisés :

| Code | Raison | Cas d'usage |
|------|--------|-------------|
| `0` | `unspecified` | Raison non précisée |
| `1` | `keyCompromise` | **Clé privée compromise** |
| `3` | `affiliationChanged` | Changement d'organisation |
| `4` | `superseded` | Remplacé par un nouveau certificat |
| `5` | `cessationOfOperation` | Serveur décommissionné |

```bash
# Révoquer avec une raison explicite (recommandé)
step ca revoke \
    --serial 1A2B3C4D5E6F \
    --reason "keyCompromise" \
    --reasonCode 1
```

## 2.5. Ce qui se passe après la révocation

step-ca expose automatiquement deux mécanismes pour que les clients vérifient la révocation :

**CRL (Certificate Revocation List) :**

```bash
# Télécharger et inspecter la CRL de step-ca
curl -o ca.crl https://step-ca.intranet.tp:9000/acme/acme/crl

# Vérifier un certificat contre la CRL
openssl verify \
    -CAfile /usr/local/share/ca-certificates/ca-intranet.crt \
    -crl_check \
    -CRLfile ca.crl \
    /etc/ssl/intranet/tp1.crt
```

**OCSP (Online Certificate Status Protocol) :**

```bash
# Interroger le serveur OCSP de step-ca
openssl ocsp \
    -issuer ~/.step/secrets/intermediate.crt \
    -cert /etc/ssl/intranet/tp1.crt \
    -url https://step-ca.intranet.tp:9000/ocsp \
    -resp_text

# Résultat attendu après révocation :
# tp1.crt: revoked
# This Update: ...
# Reason: keyCompromise
```

## 2.6. Procédure complète en cas de compromission

```
1. Isoler le serveur compromis du réseau si possible
2. Révoquer le certificat :
   step ca revoke --serial <N> --reason "keyCompromise" --reasonCode 1
3. Générer une nouvelle paire clé/certificat sur le serveur assaini
4. Vérifier que l'ancienne clé privée a été supprimée et ne peut pas être récupérée
5. Analyser comment la compromission a eu lieu (audit de sécurité)
```

> ⚠️ **Important :** révoquer le certificat n'a d'effet que si les clients vérifient effectivement la révocation (CRL ou OCSP). Un navigateur qui ne vérifie pas la CRL continuera d'accepter le certificat révoqué jusqu'à son expiration. C'est une des raisons pour lesquelles les **certificats courts** (90 jours) réduisent l'impact d'une compromission.

# 3. Challenges ACME et contraintes réseau

## 3.1. Question

**Challenge ACME sur intranet** : step-ca utilise par défaut le challenge `device-attest-01` ou `http-01`. Quelles contraintes réseau cela implique-t-il ?

## 3.2. Rappel : à quoi sert le challenge ACME ?

Avant d'émettre un certificat, step-ca doit s'assurer que le client qui demande un certificat pour `tp1.intranet.tp` **contrôle bien ce nom ou cette IP**. Le challenge est la preuve de cette maîtrise.

## 3.3. Les trois types de challenges

## 3.4. Challenge HTTP-01

**Mécanisme :**

```
1. step-ca génère un token aléatoire
2. Le client dépose un fichier à :
   http://tp1.intranet.tp/.well-known/acme-challenge/<token>
3. step-ca tente de télécharger ce fichier
4. Si le téléchargement réussit → preuve validée → certificat émis
```

**Contraintes réseau :**

```
┌─────────────┐    HTTP GET     ┌──────────────┐
│   step-ca   │ ─────────────▶ │  tp1 (port   │
│             │ ◀────────────  │  80 ouvert)  │
└─────────────┘                └──────────────┘
```

- Le **port 80 doit être ouvert** sur le serveur client
- step-ca doit pouvoir **joindre le serveur client en HTTP**
- Ne fonctionne **pas pour les certificats wildcard** (`*.intranet.tp`)
- Ne fonctionne **pas si le serveur est derrière un NAT strict** sans règle de redirection

**Configuration Apache pour exposer le challenge :**

```apache
<VirtualHost *:80>
    ServerName tp1.intranet.tp
    # Autoriser uniquement le répertoire ACME challenge
    Alias /.well-known/acme-challenge/ /var/www/acme-challenge/
    <Directory /var/www/acme-challenge/>
        Options None
        AllowOverride None
        Require all granted
    </Directory>
    # Rediriger tout le reste vers HTTPS
    RedirectMatch 301 ^(?!/\.well-known/acme-challenge/).* https://tp1.intranet.tp$0
</VirtualHost>
```

---

## 3.5. Challenge TLS-ALPN-01

**Mécanisme :**

```
1. step-ca génère un token
2. Le client crée un certificat TLS temporaire contenant le token
3. step-ca se connecte en TLS sur le port 443 avec l'extension ALPN "acme-tls/1"
4. Le client répond avec le certificat temporaire
5. step-ca vérifie le token → preuve validée
```

**Contraintes réseau :**

- Le **port 443 doit être ouvert** et accessible par step-ca
- Le serveur web doit **cesser temporairement d'écouter** sur 443 pendant le challenge
  (ou step-cli gère un serveur TLS temporaire en parallèle)
- Même limitation que HTTP-01 : **pas de wildcard**

---

## 3.6. Challenge DNS-01

**Mécanisme :**

```
1. step-ca génère un token
2. Le client crée un enregistrement DNS TXT :
   _acme-challenge.tp1.intranet.tp = <token_haché>
3. step-ca interroge le DNS pour vérifier l'enregistrement
4. Si présent → preuve validée → certificat émis
```

**Contraintes réseau :**

```
┌─────────────┐   DNS query     ┌──────────────┐
│   step-ca   │ ─────────────▶ │  Serveur DNS  │
│             │ ◀────────────  │  de l'intranet│
└─────────────┘                └──────────────┘
```

- **Aucun port ouvert requis** sur le serveur client
- step-ca doit pouvoir **interroger le serveur DNS** de la zone
- Fonctionne pour les **certificats wildcard** (`*.intranet.tp`)
- Nécessite une **API DNS** pour automatiser la création des enregistrements TXT
  (BIND avec `nsupdate`, PowerDNS API, etc.)

**Exemple avec nsupdate (BIND) :**

```bash
# Créer l'enregistrement TXT pour le challenge
nsupdate -k /etc/bind/ddns.key << EOF
server 192.168.1.1
zone intranet.tp.
update add _acme-challenge.tp1.intranet.tp. 60 TXT "token_valeur_ici"
send
EOF
```

---

## 3.7. Tableau de synthèse

| Challenge | Port requis | Wildcard | Automatisable | Cas d'usage intranet |
|-----------|-------------|----------|---------------|----------------------|
| HTTP-01 | 80 (TCP) | ❌ | ✅ Facile | Serveurs web standards |
| TLS-ALPN-01 | 443 (TCP) | ❌ | ✅ Moyen | Serveurs HTTPS uniquement |
| DNS-01 | Aucun | ✅ | ✅ Si API DNS | Wildcards, serveurs isolés |

> **Recommandation pour le TP :** utiliser **HTTP-01** si tous les serveurs sont sur le même réseau que step-ca (c'est le cas en intranet TP). Utiliser **DNS-01** si vous souhaitez émettre un certificat wildcard `*.intranet.tp` couvrant tous les serveurs du TP.

# 4. Windows Server / IIS et Certbot

## 4.1. Question

**Windows Server** : comment intégrer un serveur IIS dans cette architecture ? Certbot existe-t-il pour Windows ?

## 4.2. Certbot existe-t-il pour Windows ?

Oui. Certbot propose un installeur Windows (`.exe`) depuis la version 1.9. Il fonctionne en ligne de commande PowerShell ou CMD.

```powershell
# Télécharger l'installeur depuis https://certbot.eff.org/
# Puis dans PowerShell (en tant qu'administrateur) :

certbot --version
```

## 4.3. Configurer Certbot sur Windows pour pointer vers step-ca

```powershell
# Obtenir un certificat pour IIS via step-ca
certbot certonly `
    --standalone `
    --server https://step-ca.intranet.tp:9000/acme/acme/directory `
    -d tp1.intranet.tp `
    --agree-tos `
    --email admin@intranet.tp
```

> **`--standalone`** : certbot lance son propre mini-serveur HTTP sur le port 80 pour répondre au challenge HTTP-01. IIS doit être **arrêté temporairement** pendant cette opération, ou utiliser le challenge DNS-01.

**Pour éviter d'arrêter IIS**, utiliser le plugin `--webroot` :

```powershell
certbot certonly `
    --webroot `
    --webroot-path C:\inetpub\wwwroot `
    --server https://step-ca.intranet.tp:9000/acme/acme/directory `
    -d tp1.intranet.tp
```

Les certificats sont déposés dans :
```
C:\Certbot\live\tp1.intranet.tp\
├── cert.pem      ← certificat serveur
├── chain.pem     ← certificat CA intermédiaire
├── fullchain.pem ← cert + chain concaténés
└── privkey.pem   ← clé privée
```

## 4.4. Importer le certificat dans IIS

IIS n'utilise pas directement des fichiers `.pem`. Il faut d'abord **convertir en PKCS#12** (`.pfx`) :

```powershell
# Convertir PEM → PFX
openssl pkcs12 -export `
    -in C:\Certbot\live\tp1.intranet.tp\fullchain.pem `
    -inkey C:\Certbot\live\tp1.intranet.tp\privkey.pem `
    -out C:\ssl\tp1.pfx `
    -passout pass:MotDePassePFX
```

Puis dans IIS Manager :

```
IIS Manager
└── Connexions → <Nom du serveur>
    └── Certificats de serveur
        └── Importer → sélectionner tp1.pfx → saisir le mot de passe
```

Ou en PowerShell :

```powershell
# Importer le PFX dans le magasin Windows
Import-PfxCertificate `
    -FilePath C:\ssl\tp1.pfx `
    -CertStoreLocation Cert:\LocalMachine\My `
    -Password (ConvertTo-SecureString -String "MotDePassePFX" -AsPlainText -Force)

# Récupérer le thumbprint du certificat importé
$thumb = (Get-ChildItem Cert:\LocalMachine\My | `
    Where-Object { $_.Subject -like "*tp1.intranet.tp*" }).Thumbprint

# Lier le certificat au site IIS
Import-Module WebAdministration
Set-Item "IIS:\SslBindings\0.0.0.0!443" -Value (Get-Item Cert:\LocalMachine\My\$thumb)
```

## 4.5. Automatiser le renouvellement sur Windows

Certbot crée automatiquement une **tâche planifiée Windows** lors de son installation. Vérifiez-la :

```powershell
# Vérifier la tâche planifiée Certbot
Get-ScheduledTask -TaskName "Certbot Renew Task"

# Tester le renouvellement manuellement
certbot renew --dry-run `
    --server https://step-ca.intranet.tp:9000/acme/acme/directory
```

Le problème avec IIS est qu'après renouvellement, le nouveau `.pem` doit être **réimporté en PFX** et **rebindé dans IIS**. Automatisez cela avec un script PowerShell appelé par Certbot via `--deploy-hook` :

```powershell
# C:\scripts\deploy-cert-iis.ps1
param(
    [string]$Domain = $env:RENEWED_LINEAGE
)

$certPath = "$Domain\fullchain.pem"
$keyPath  = "$Domain\privkey.pem"
$pfxPath  = "C:\ssl\$($Domain | Split-Path -Leaf).pfx"
$pfxPass  = "MotDePassePFX"

# Convertir en PFX
& openssl pkcs12 -export `
    -in $certPath -inkey $keyPath `
    -out $pfxPath -passout "pass:$pfxPass"

# Importer dans le magasin Windows
$secPass = ConvertTo-SecureString $pfxPass -AsPlainText -Force
$cert = Import-PfxCertificate -FilePath $pfxPath `
    -CertStoreLocation Cert:\LocalMachine\My -Password $secPass

# Rebinder dans IIS
Import-Module WebAdministration
Set-Item "IIS:\SslBindings\0.0.0.0!443" -Value $cert

# Redémarrer IIS pour prendre en compte
iisreset /noforce

Write-Host "Certificat renouvelé et déployé sur IIS : $($cert.Thumbprint)"
```

```powershell
# Appeler ce script automatiquement après chaque renouvellement
certbot renew `
    --server https://step-ca.intranet.tp:9000/acme/acme/directory `
    --deploy-hook "powershell -File C:\scripts\deploy-cert-iis.ps1"
```

## 4.6. Faire confiance à la CA racine sur Windows

Avant toute chose, la CA racine OpenSSL doit être importée dans le magasin Windows :

```powershell
# Importer ca.crt dans les autorités racines de confiance
Import-Certificate `
    -FilePath C:\ssl\ca.crt `
    -CertStoreLocation Cert:\LocalMachine\Root
```

Ou via GPO (Group Policy Object) pour déployer sur tous les postes du domaine en une seule opération :

```
Stratégie de groupe
└── Configuration ordinateur
    └── Paramètres Windows
        └── Paramètres de sécurité
            └── Stratégies de clé publique
                └── Autorités de certification racines de confiance
                    └── Importer → ca.crt
```

## 4.7. Récapitulatif Windows / IIS

```
Étapes pour intégrer IIS dans l'architecture step-ca :

1. Installer Certbot pour Windows
2. Importer ca.crt dans Cert:\LocalMachine\Root
3. Obtenir le premier certificat (--webroot ou --standalone)
4. Convertir PEM → PFX et importer dans IIS
5. Créer le script PowerShell de déploiement automatique
6. Configurer --deploy-hook dans Certbot
7. Vérifier la tâche planifiée de renouvellement
```
